# 意图门的有效性与优化选项

日期：2026-10-27。性质：研究与方案比较，不是已批准需求、实施计划或运行验收。未修改 preset、persona、watchdog、依赖或日常 profile。

后续：[方案 B 可行性核验](2026-10-27-intent-gate-b-feasibility.md)已找到官方输出流扩展点并完成离线核心链路探针；本文保留方案比较时的判断，新增工程证据以该报告为准。

## 结论

建议保留“行动前把理解说具体”的机制，但目前不能宣称本插件的意图门已提高任务成功率。公开研究提供间接支持；当前代码和测试主要证明声明的识别与拒绝规则。声明出现率、理解正确率、最终任务成功率，是三个不同指标。

最推荐的目标是 **B：请求级理解声明 + 执行前输出校验**。保留具象化首句，把校验前移到整段工具程序执行之前；理解出现变化时允许修正。宿主若没有可用的输出拦截扩展点，则先用 A 做低成本试验，不能通过复制或 fork DSH 来实现 B。

## 原始设计与本地迁移的区别

[Sisyphus default.ts 固定快照](https://github.com/code-yeongyu/oh-my-openagent/blob/f2a7ec093af56598b649a3e84920b589b6f37e44/packages/omo-opencode/src/agents/sisyphus/default.ts)要求先识别真实意图、公开说明路由；其说明直接把“锚定路由”和“向用户透明”作为目的。这证明设计意图，不能当作收益实验。

本插件的直接迁入基线是 dsh-ptc-roles，不是当前 Sisyphus 的逐行移植，见[基础规格](../specs/2026-10-22-ptc-hashline-requirements-spec.md)与 [ADR-0002](../adr/0002-own-ptc-gate-assets.md)。不能把本地 pwsh 拦截规则自动归因给 oh-my-openagent。

本地 [persona](../../presets/ptc-hashline/personas/orchestrator.md)已经要求“用户要的结果 + 理解依据 + 接下来做法”，也已有灰区自述。优化重点不应只是再添加相同提示，而应改进触发范围、执行时机、纠偏规则和收益判据。

## 是否有效：分别看三种作用

| 目标 | 判断 | 证据边界 |
|---|---|---|
| 让用户知道 agent 怎么理解任务 | 有直接交互价值，前提是首句具体且确实展示 | 用户能看到解读；能否及时发现并阻止错误还取决于界面、用户注意和可中断时机 |
| 让 agent 后续执行围绕明确目标 | 有合理机制和间接实证支持 | 没有本插件首句机制的受控因果实验，不能给收益百分比 |
| 用工具拒绝保证理解正确 | 当前机制做不到 | 正则验证首行前缀与分类，不验证目标、约束、授权或后续行为是否一致 |

[Rephrase and Respond](https://arxiv.org/abs/2311.04205)在问答与推理任务中研究先重述再作答，提供相关支持，但其重述长度、任务和模型都不同于本插件的一句声明。

[Intent Mismatch Causes LLMs to Get Lost in Multi-Turn Conversation](https://arxiv.org/html/2602.07338v1)报告将意图理解与执行分开的框架可改善其多轮基准；它还依赖专门的 Mediator 与经验提炼，不是简单前缀效果。

风险同样真实：[LLMs Get Lost In Multi-Turn Conversation](https://arxiv.org/abs/2505.06120)发现模型容易过早形成假设并过度依赖早期答案。对本机制的设计推断是：正确理解可以帮助聚焦，错误理解也可能被强化，必须允许根据用户纠正和新证据更新。

以上研究不能推出“首句一定有益”，更不能推出 ASCII 标记、六桶或拒绝 pwsh 本身有益。对现代编码模型、真实使用者和本插件的净收益仍记 GAP。

## 当前实现与原意的偏差

1. **按工具决定是否需要解释理解。** [watchdog](../../presets/ptc-hashline/intent-gate-watchdog.mjs)的 BEHAVIOR_TOOLS 含 pwsh/bash，但没有 read/grep/run_code。相同任务用不同工具会获得不同待遇；纯回答里的误解也可能不受提醒。对“让理解可见”的目标，这个代理指标不完整。
2. **格式合规不能代表语义合规。** GATE_LINE_RE 只检查首行 Intent: 和英文桶；“Intent: fix”就能通过，即使没有说明要解决什么问题。六桶适合统计，但不足以描述目标、交付物和约束；混合请求也不必强压成单一权限判断。
3. **发现得太晚。** tools/pre-execute 在内层工具到达时拒绝。程序可能已经执行了其他调用；程序失败也不代表先前副作用回滚。存量[本地问题记录](../../.scratch/hashline-default-editing/2026-10-24-hashline-usage-problems-and-improvements.md)的 P3-2/P3-4/G11 记录了成本和 catch 边界；该文件被忽略，不随 clone 交付。
4. **有可见性，不等于形成确认闭环。** 声明与调用同次生成时，用户可能来不及纠正，工具就开始运行。因此普通任务可主动继续，关键歧义或高影响决策则需真正等待澄清，不能把“用户没有打断”当同意。
5. **持续性证据不足。** 源码头部记载旧会话 26 轮只在最初两轮出现门行，这是作者记录，不是本轮独立复验；说明需要约束持续性，但不能证明当前拒绝机制有净收益。每轮只拒一次也说明它是纪律措施，不是理解或权限保证。

## 多个可选优化方案

| 选项 | 做法 | 收益与代价 | 适用判断 |
|---|---|---|---|
| A：首句规则精简 + 请求前提醒 + 观察 | 每个新用户请求首次回复都用自然语言说明结果和下一步；不在内层工具制造拒绝，记录漏报和误解 | 低改造成本、减少程序中断；仍可能被模型忽略 | 最适合快速小样本试验，也可作为 B 缺少宿主扩展点时的过渡 |
| **B：请求级声明 + 执行前输出校验（最推荐）** | 在输出展示及整段程序派发前检查声明，缺失时让模型补写；不执行旧程序，重新生成并检查调用 | 兼顾持续性与低中断成本；需要真实宿主扩展点，不能只换一句正则 | 推荐目标；须先证明扩展点与消息/工具顺序可行 |
| C：结构化意图卡片 | 模型给出 outcome、deliverable、constraints、assumptions、nextAction 等字段，宿主渲染自然语言首句，分类留作元数据 | 字段可校验、便于日志与 UI；需要更多协议和展示改造，完整字段仍不保证理解正确 | 适合将来要做任务面板、跨轮恢复或严格审计时 |
| D：独立意图解释/语义审核层 | 另一个模型对照用户原话检查目标、约束和首个动作，仅在复杂/含糊任务触发 | 可检查正则看不到的偏差；增加延迟、费用和审核误判，审核器也可能误解 | 不建议默认启用，可在高误解成本场景试验 |

B 不是自动让首句“更聪明”；它只让一份可审视的理解更可靠地出现在行动之前。语义收益依赖提示内容、修正规则和实测。C/D 也不能把模型生成的理解升级为用户授权。

## 推荐方案 B 的具体行为

**频率：每个新用户请求首次可见回复一次。** 工具结果、后台通知、同请求的进度和收尾不重贴整句。用户纠正目标时立即更新；“继续”承接已经确认的目标和限制，不能无条件清空历史授权或自动扩大范围。若用户确实希望每条进度消息也有首句，可简述该步目的，但通常会增加重复，应单独测试。

**内容：具体结果 + 关键边界或假设 + 下一步。** 简单任务一句话即可；只有有区分价值时才写依据和不确定项。避免只说“我会分析一下”，也避免每次强迫用户读英文分类与格式说明。分类可保留在内部元数据；迁移初期也可暂时保留 Intent: 前缀以降低变化面。

本次请求的合格例子：“你希望判断意图声明是否能减少理解偏差，并比较值得实施的改进方案；我会结合实现和研究给出证据边界与推荐。”

有歧义的例子：“我先把‘优化’理解为减少等待时间；若你指的是降低费用，方案会不同，我会先确认这一点。”关键是说明两种解读导致什么差异，不能用一句“有误请纠正”代替必要澄清。

**锚定目标，允许方法变更。** 新证据推翻假设时，简述“原先理解—新证据—调整后的做法”；不为维护开场承诺继续走错路。用户纠正优先于旧声明，原始请求始终保留为依据。

**校验前移，修复有界。** 理想链路是“用户请求 → 生成声明与调用 → 校验 → 展示声明 → 派发程序”。缺声明时不派发程序，给模型一次修复机会；旧调用作废，重新生成并再次校验。仍失败则明确报告本轮协议失败，不静默补写一行假装模型理解，也不无限重试。恢复策略是待试验的方案，尚未实施。

当前 session/event 是观察入口，agent/pre-step 在生成前，而 tools/pre-execute 的内层拒绝已经太晚。仓库证据未证明存在可直接拦截最终助手消息、取消其调用并重新生成的官方扩展点；B 的可实现性保留 GAP。只校验外层 run_code 能覆盖工具程序，但不能据此宣称覆盖无工具答案。

**保留独立授权与执行策略。** intent 是用户可读的理解摘要；分类词不能决定权限。只在有关键缺失或歧义时等待用户，普通明确任务继续工作；出现声明不代表用户批准了其中新增的范围。

## 怎样判断优化真的有效

建议先做小规模探索，不自动重启已经收尾的 S0/S1/S2，也不现在发起付费评测。可使用 30～50 个预先标注的代表性请求作成本可控的试验，数量只是试点建议，不能据此保证统计显著。

覆盖纯解释、诊断但不修复、明确修改、多目标混合、模糊请求、长会话用户纠正、继续执行、PTC 混合工具。固定模型、工具、预算与任务，随机安排并重复采样，分别记录结果。

比较四臂：无声明机制、当前机制、新首句规则但无输出闸门、新规则加 B。后两臂的差异才能估计输出闸门增量；当前机制与新规则之间同时改变了内容和触发范围，不能把差异全归因于某一个因素。

主要指标应是意图误读率、关键约束遗漏、未经请求的范围扩张、最终任务正确率，以及用户纠正后能否恢复。人工盲评结合文件与执行轨迹，语义评审模型只作辅助。

同时统计首句有用率、声明覆盖率、错误锚定持续轮数、程序中断/重试、Token、耗时和用户阅读负担。“首句有用”要求用户能从中区分至少两种会导致不同工作的解读，不能仅由正则通过决定。

只有在理解/任务指标改善、且成本与误拒可接受时，才将 B 升为默认；若只提高声明出现率，应报告“格式/可见性改善”，保留有效性 GAP。

## 本轮证据与实施边界

本轮新增的是公开源码固定快照、相关论文与本地机制的对照分析；没有重演旧会话，也没有进行新的真实模型 A/B。上轮 10 组钩子探针只证明识别规则；上轮 PTC 测试 3 PASS / 2 FAIL，编辑失败原因未在本轮调查，不用它证明有效性或错误锚定。

现行[基础规格 FR-1](../specs/2026-10-22-ptc-hashline-requirements-spec.md)及 [ADR-0002](../adr/0002-own-ptc-gate-assets.md)要求继承原判据和资源，A/B/C 的实施会改变基线。若选定实施，应先修订需求、资源摘要检查与验收约定；本研究不改写现行要求，也不构成升级目标切换授权。
