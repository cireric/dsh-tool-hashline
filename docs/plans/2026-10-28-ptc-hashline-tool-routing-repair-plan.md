# PTC Hashline 工具路径修复计划

日期：2026-10-28。状态：**计划已整理，尚未实施**。

关联：[意图门修复计划](2026-10-28-intent-gate-repair-implementation-plan.md)。两条工作线共享 persona、实际请求与运行轨迹，但分别验收。本轮新增的是计划安排，不是产品修改、运行目标切换或真实模型调用授权。

需求依据：[项目 README](../../README.md)、[基础规格](../specs/2026-10-22-ptc-hashline-requirements-spec.md)、[默认编辑策略 §1.1](../specs/2026-10-24-hashline-default-editing.md)、[兼容规则](../../tests/compat/README.md)。既有行为纪律已经禁止通过原生 Node FS、shell 等入口规避编辑策略；首版没有承诺全面阻断所有旁路。

## 1. 目标与已有证据

目标是让文件任务在 run_code 内采用适用的 SDK 工具，尤其既有普通文本更新进入 read → edit 的 Hashline 路径；保留 PTC 编排、canonical value、有效 cwd、共享物理引擎、tag/seen 既有边界和受控降级规则。

本地依据：[独立复核报告](../../.scratch/investigations/2026-10-28-ptc-hashline-tools-not-used-recheck.md)、[冻结统计](../../.scratch/investigations/2026-10-28-tools-usage-recheck.json)。这些是本机原始材料，不随 clone 交付；后续实施须将必要脱敏事实与重跑入口写入正式验收，不依赖私人路径才能理解方案。

已证实的范围：

- 冻结统计中 7 个目标 preset 会话共 519 个顶层调用，全部 run_code；内部 read/edit/write/grep/glob/pwsh 派发为零，但使用过其他 SDK 工具。因此问题是文件工具采用，不能称完全没有 SDK。
- 关键文件会话实际收到 read/edit SDK 和禁止原生 Node 改状态的要求；seq 263/264 有原生 FS 写入及成功返回配对。现有证据不能解释模型内部为何忽略要求。
- SDK 枚举存在不等于 read/edit 全路径可用，本轮前尚缺该场景的当前完整宿主执行复验。
- 复核时已安装配置校验器只接受 native/ptc，拒绝 both。保留 ptc 基线，不把切换呈现档作为修复。
- 网络调研等无需文件操作的任务，不应因 read/edit 为零判失败。历史 421/209/182 个原生 FS/子进程/写 API 文本信号只是静态候选，不能当实际副作用计数。

## 2. 期望工具路径

| 任务 | 期望路径 | 适用边界 |
|---|---|---|
| 读取普通文本 | tools.read，消费 canonical value/nextAction | 按窗口补读；显示与 seen 不是完整权限边界 |
| 文件发现/内容搜索 | tools.glob / tools.grep 按需要使用 | 不为增加调用率强制两者都调用；也不要求每次文件任务都搜索 |
| 既有普通文本局部更新 | tools.read → tools.edit，默认 Hashline | 参数、tag/锚点来自实际 SDK 与读取结果；受控降级按既有规格 |
| 真正新建文件 | 既有创建工具与创建契约 | 不用 write 覆盖既有内容来绕开默认编辑策略 |
| 运行 git、构建与测试 | 平台 shell SDK：Windows 为 tools.pwsh，其他平台按实际注册工具 | 不以原生 child_process 替代正式 shell 工具；shell 也不能承担规避策略的文本更新 |
| 数据整理、字符串/数组计算 | run_code 内纯计算 | 对已获数据计算不需要伪造工具调用；实际任务文件读取/写入与计算区分 |
| 网页调研、专用外部任务 | 相应 SDK/专用工具 | 无文件需求时文件工具为零可以合格 |
| 关键歧义 | 问题专用 run_code 调用 tools.ask_user_question | 问题未解决前不执行相关业务工具；声明专用修复阶段仍完全不提供工具 |

上述表是行为路径，不新增工具名、返回 schema、策略豁免或运行时依赖。不能因工具返回错误就静默改走 fs/child_process；先核验并解决错误本身，无法解决时如实报告任务受阻。

## 3. 工作包

### T0：核验实际 SDK 可用性并冻结目标边界

在独立打包安装、完整 preset、官方 launcher/registry/loader 与官方进程 PTC 中，保存实际请求的 SDK 声明及工具参数、版本/realpath/资源摘要。分别执行一次普通文本 read、适用 edit、创建、搜索和平台 shell；只操作隔离夹具，不动用户文件或日常 profile。

用独立文件检查确认 read/edit 的 cwd、canonical value 与结果；复用现有引擎身份和策略测试证明同一物理 hashline 实例，不由“工具键存在”推断可用。若 SDK 接口或安装失败，先将实现/配置问题修复，不能把全部原因归给模型偏好。

同时确认“业务任务文件”与正常构建/测试产物、图像/Office 等专用工具输出的界限；沿用已有例外，不臆造全面禁止 Node 或 shell 的新权限模型。

**完成条件**：SDK 可见性与执行能力分别有证据、失败责任可定位；普通 fixture 更新进入真实受管 edit。若接口有缺口，仅阻塞依赖该接口的包。

### T1：统一 persona 的实际操作路径（依赖 T0；与意图门 P1 同一次协调修改）

把泛化的“行为改变走 tools.*”落实为上一表的正向操作指引与最短示例：普通读取、既有文本更新、搜索、shell 和问题专用程序。示例参数必须从当前 SDK 与 canonical value 提取，不能凭记忆编造字段；保持工具失败可见及既有 try/catch 约定。

协调：read/edit 的应用范围与受控降级、提问允许 SDK 包装程序、声明专用修复无工具、业务续步恢复相应工具。不要在两条计划中各维护一份互相冲突的 persona。

检查实际 assemble 后的提示/SDK，而非只读源码文件。旧提示已明确禁止旁路，所以此次提示修改只是候选干预，不能预先宣称有效。

**完成条件**：实际请求体现统一路径，契约测试无矛盾，资源 digest 同步；真实模型采用是否改善留待 T4。

### T2：建立按任务目标判读的可复核证据（依赖 T0）

复用现有 session-log 解码器、运行证据提取与评测驱动；只补当前缺失的判读，不另造日志系统。区分顶层 run_code、内层派发 start/settle、程序开始、独立文件副作用与请求结果。

同一 subCallId 的 start/settle 配成一次调用；开始未结算、取消后残留及证据缺口明确记 unknown/GAP。SDK 枚举、描述字符串、代码正则命中不能当实际工具执行或副作用证明。

按“任务目标＋目标文件”分母统计：适用工具路径、正常例外、无需文件操作、适用性未知；独立记录工具采用、业务正确与旁路。read/edit 各出现一次不代表整个修改路径合格，先工具读再 fs 写、先 edit 再 shell 覆盖均需识别。

**完成条件**：固定数据能稳定区分上述正反例，证据缺失不能记零旁路。原始代码/命令不自动完整导出，脱敏事实足以定位时只保存必要摘要。

### T3：固定适配器完整宿主验收（依赖 T1/T2；与意图门 P5 合并装配）

固定适配器提供已知程序，证明 SDK、工具观察与策略流程；它不能证明模型会主动选择工具。新负向例先在旧判读/约束下暴露缺口，再实现与复核，不能靠只数工具名给出 PASS。

必须包含交叉场景：

- 未通过声明的旧 read/edit 程序零启动；修复无工具，声明通过后只执行新生成程序。
- 关键歧义先 question-only 程序；回答前没有相关 read/edit/write/shell 更新；答案明确后再生成受管编辑。
- 修复后仍未知用户选择时继续澄清，不能以 SDK 恢复为由自动改文件。
- 工具失败、tag 漂移、窗口受限按 nextAction/既有降级规则处理，不静默改用原生 FS 或 shell 更新。
- 真正创建、构建产物与专用任务正常工作，纯网络任务不因无文件工具被误判。

采用 README 完整门禁与 test:delivery；涉及 persona/preset/运行契约时不能只跑文案测试。隔离副本构建，不热改运行宿主。两个计划可以复用同一未变化最终组合的本轮门禁证据，但各自逐项映射，不能重复累加成更多覆盖。

**完成条件**：SDK 全链路、独立结果与证据判读通过；明确尚未证明真实模型采用，也不声称已全面机械阻断旁路。

### T4：真实模型的路径采用验收（可先准备；执行需冻结模型与预算）

建议 8 类任务各两个独立会话：文本读取、文件发现/搜索、既有单点更新、连续/多文件更新、真正创建、外部漂移或工具错误后的恢复、git/构建/测试、纯网络调研。意图门 P6 的澄清/等待案例补充工具轨迹判读，能共用的真实运行只计一次成本。

16 条新增对话各最多 6 次模型生成，总上限 96 次；若与意图门建议的 24 条全部分别执行，名义上限为 240 次生成，不是原预算已覆盖的免费追加。运行前用联合 manifest 去重并冻结模型、provider、reasoning、实际 SDK、文件初态、独立 expected、调用/输入输出 token/货币/时间上限；参数或预算未批准时不调用模型。

通过条件：所有已知适用文件目标实际使用相应 SDK 路径；适用既有文本更新按 Hashline/受控降级规则处理；真实目标文件独立检查正确；没有以原生 FS、子进程或 shell 文本覆盖规避。正常例外与无需文件操作任务按其预期合格，证据缺失记 GAP，不能按未发生处理。

这只证明冻结集合上的采用与正确性；没有同条件对照不宣称提升率，没有覆盖所有入口不宣称完整隔离。任一关键项失败即记录 FAIL，不通过追加提示后原地重跑并混入原分母“洗绿”。

**完成条件**：工具采用、Hashline 适用性、业务正确、旁路、耗时与成本分开报告；与意图门语义/等待结果联合审阅。

## 4. 机械约束的边界

本轮实施方向先覆盖已有行为纪律、实际 SDK 可用性与采用验收。若 T4 仍出现旁路，不能声称工具问题已修复；记录 FAIL 并给出下一项有证据的干预。

若用户要求“任何程序都无法绕过”，必须另立运行时/文件系统范围规格，覆盖动态导入、别名、子进程、shell、构建产物、专用工具、读观察与写入授权。这超出当前“首版不全面阻断”的承诺，不能把静态扫描、提醒或强制 tools.pwsh 当成同等保证。

可评估官方已有的受限 runtime 能力，但先核验功能、兼容与真实解析身份。没有可满足需求的官方接口时报告缺口，不复制/fork/修改 DSH 本体，不未经同意升级或切换目标。
