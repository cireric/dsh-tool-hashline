# 意图门修复实施计划：歧义澄清、等待保真与内部恢复

日期：2026-10-28。

状态：**计划已整理，产品实现未开始**。本次授权范围是全面分析与制定计划；本文不是安装、重启、发布、目标切换或真实模型调用授权。后续收到实施指令时按工作包推进，不重新访谈已经确认的需求。

需求权威：[请求级意图门规格](../specs/2026-10-27-intent-gate-b-requirements.md)。本计划承接用户本轮补充：支付示例用于测试歧义，合理输入应得到解读差异与真实意图询问，不能被粗暴显示为 error。新增体验要求须在 P0 写入正式规格后实施；计划不自行取代规格。

## 1. 本次修复要交付什么

修复完成后，用户应观察到以下行为：

1. 关键歧义出现时，同一主 agent 列出有依据的解读及其工作差异，询问真实意图；必需信息缺失时直接问缺失项。普通明确请求直接推进。
2. 澄清是正常交互，问题提出后等待回答；“继续”“收到”、沉默、插件通知或其他问题的结算都不能替用户作选择。
3. 声明格式失配属于模型输出协议问题。首次可恢复失配在请求层呈现为恢复中，不先把用户请求宣布 Failed；恢复不放行旧正文或旧调用。
4. 声明合格不等于理解正确、不等于答案已给出，也不等于获准执行。语义行为、等待约束和格式恢复分别验收。

本次沿用一次自动声明修复、同主 agent、不增加语义审核模型、严格展示前校验、原授权不扩大、真实故障保真及既有 read/edit 契约。正常首次合格路径不统一增加一次模型生成。

工具未采用问题另有[工具路径修复计划](2026-10-28-ptc-hashline-tool-routing-repair-plan.md)，与本文联合实施和验收。明确的文件任务不仅要理解正确，还应实际进入适用的 SDK/Hashline 路径；顶层保留 run_code。两者目前没有已证实的共同根因，不能互相替代修复。

## 3. 支付示例的验收预期

冻结用户原话：

> 老板在群里说：“下周先别上支付，等风控确认；但如果业务非要上，至少把开关和回滚做好，灰度别超过 10%。”
> 根据上面要求，帮我判断支付功能下周能不能上线，列出上线前必须做的事，并安排灰度。

正确识别为“默认暂缓 + 条件例外”，不是凭空制造老板自相矛盾。需要确认例外是否已经启动，以及用户希望评估的决策路径；风控结果等必需事实不可编造。

示例首答的目标形状：简短声明“先确认默认暂缓与例外上线的适用路径”，指出两种工作差异，再问：“目前业务方是否已经明确要求下周上线，还是仍按风控未确认的默认暂缓来评估？”措辞可以变化，不匹配固定句子。

用户未回答前，不给无条件上线结论、不虚构批准、不将假设排期写成已决定的计划。可简述两条条件路径帮助用户选择；如果用户明确要求“分别分析两条路径”，按条件分析交付，不强迫再选一条。10% 已知上限不重复询问。

## 4. 状态与职责设计

### 4.1 分开维护语义等待与格式恢复

语义路径：理解请求 → 明确则推进；存在关键歧义/必需信息缺失则提问 → 等待 → 读取答案并更新理解 → 推进或继续问缺失项。

格式路径：需要声明的回复待检查 → 合格则发布；失配则扣下旧内容、花一次预算、声明专用修复 → 发布合格声明后继续；耗尽则协议暂停。格式恢复不能将尚未解决的业务歧义改成“已选择”。

保持既有纯社交/普通继续例外与新约束优先级。这里的“用户输入开启声明机会”与“旧业务问题已解决”是不同事实：新输入可以欠新声明，但旧问题不能仅因此消失。

### 4.2 问题必须有可核对的归属

优先复用宿主问题服务、问题 callId/subCallId、来源消息 ID 与正式记录，不建立独立通用工作流系统。P0 必须明确：

- 待答问题归属哪个原请求，后续输入是匹配答案、补充约束、取消原任务还是独立请求。
- 答案来源与 pending/answered/cancelled/dismissed/错误等宿主结果的真实形状；外层结果按 toolCallId 配对，PTC 按 subCallId 配对，不能仅按工具名结束等待。
- 显式选中的选项与自由文本回答的区别；选项恰叫“继续”时不能误伤真实选择，裸“继续”也不能伪装成选择。
- 当前独立请求可推进，同时保留旧问题及其约束。只支持一个激活请求的宿主不能靠清空旧问题假装满足此要求。

匹配 ID 只能证明关联，不能证明自由文本语义充分。该判断仍由同主 agent 完成；不把自然语言答案自动映射到推荐项，不增加第二个语义判别模型。

### 4.3 提问程序与业务动作分开

允许只承载 `tools.ask_user_question` 的 run_code；问题正文应对用户可见，相关业务动作等答案处理后重新生成。问题工具返回后的同一程序不得顺带执行依赖答案的更新/委派。

实现应利用正式工具派发边界约束问题阶段及后续步骤，而非靠扫描字符串识别代码。原生 Node/子进程旁路属于已知边界，本次不把意图门变成完整文件系统隔离系统，也不以这些旁路制造通过证据。

### 4.4 请求层呈现

| 状态 | 用户看到什么 | 运行约束 |
|---|---|---|
| 需要澄清 | 合理解释、工作差异、具体问题 | 等答案，不显示失败 |
| 正在内部修复格式 | 简短恢复状态或加载提示 | 不发布旧正文、不执行旧调用 |
| 声明恢复成功 | 已接受的真实声明，随后澄清或业务响应 | 按仍存在的等待和最新约束继续 |
| 修复耗尽 | “意图声明未能生成，工作尚未执行” | 有界协议暂停，不冒充业务结论 |
| provider 故障/取消/截断/超限 | 各自真实原因 | 不伪装成缺声明，不自动获得新预算 |

## 5. 工作包与完成条件

### P0：固定基线、对齐契约并核验接口

输入：正式需求、ADR-0006、此次分析、本轮两个探针、当前 README 和兼容规则。

工作：

1. 保存工作树及已安装/隔离候选的实际解析路径、版本、watchdog/persona/preset/宿主入口摘要。用户已有修改不是可丢弃的基线；不重置、不构建运行中宿主链接树。
2. 修订正式规格的 IG-B-03/05/06/07/14/16/17/18 及验收，明确歧义是正常交互、非答案不解决问题、首次可恢复格式失配不宣布业务失败。清理互相冲突的当前状态描述；保留历史时点。
3. ADR-0006 明确接受过“terminal 后 followup”的代价，本次需重新对齐该决定。保留无工具修复、预算与成本契约，不借修复取消严格展示保证。
4. 在隔离完整宿主核验问题服务的真实调用/答案/取消/恢复事件，以及独立请求关联能力。先检查包真实解析位置，不按目录缺失断言能力不存在。
5. 验证不伪造消息的官方恢复入口：被拒 attempt 保留后能否继续一个重建工具目录的新 step；并验证实际 CLI/Web 的恢复状态呈现入口。

恢复路线出口：

| 路线 | 采用条件 | 不得作出的替代 |
|---|---|---|
| 同 turn 内正式进入新 step | 官方入口确实支持扣下 attempt、重组 tools、持久化/取消/成本；完整宿主探针证明无首次 error 终态 | 不能把普通 retry 当成新 step，也不能用空 assistant/message 伪造成功 |
| 请求层聚合多个真实 turn | 仅当官方扩展点能显示 recovering 并关联后续修复；保留底层真实失败记录，取消也能阻止已排队 followup | 不能全局隐藏错误码、删除历史失败，或声称底层 turn 从未结束 |
| 两条路线都不能满足 | 标明具体接口、产生点、最小缺口，UX 分支记 BLOCKED，提交需要重对齐的选项 | 不复制/fork/修改 DSH 本体，不擅自降级严格要求或切换宿主版本 |

现有证据只确认普通 retry 复用 assembly.tools，不能直接撤销工具；同 turn 方案目前为 GAP。修改宿主本体不在既有授权/规格范围，不能由本计划隐含批准。若必须上游增加接口，另提交提案，本项目不热改宿主绕过。

**完成条件**：需求差异表、接口身份、问题事件样本、恢复路线探针及明确 PASS/GAP/BLOCKED；不依赖 UX 接口的语义与等待工作可以继续。

### P1：让主 agent 正确选择澄清或推进（依赖 P0 的行为契约）

修改 persona 的 Phase 0，优先呈现“明确则推进／关键歧义则解释差异并问／缺事实则先自查或问缺项”。保留目标、交付物、对象、范围、完成标准五项短检查，不增加长推理输出或第二模型。

协调三个冲突：允许问题专用程序；声明优先于“no status updates”；声明专用修复可以明确“先确认例外是否成立”，不能强迫先选一条业务路径。正常业务续步仍可能需要提问，修复完成不是自动执行许可。

增加支付示例、明确支付反例、仅做条件分析、单项信息缺失与等价实现的成对案例。提示契约测试验证指引可执行；不靠句子精确匹配宣称语义通过。

**完成条件**：无互斥指引；明确请求不统一多一次生成；合格 Intent 但漏问的样例在语义判读中明确 FAIL。实际模型是否改善留待 P6。

### P2：修复等待、答案关联与提问边界（依赖 P0 的问题接口）

先将本轮“q1 未结算 + 裸继续 + 有 Intent 行动”升级为完整宿主失败用例，再实现。逐步替换无条件清空等待的逻辑，按实际问题身份结算，保留待确认事项与原约束。

覆盖：未回答、含糊回答、自由补充、明确选择、同名选项、错 callId、陈旧结果、取消/拒答、同会话独立任务及多会话。裸继续不是选择；明确取消原目标可结束该目标，不能保留永久锁。

提问后的同一程序后续相关工具必须零执行；只有进入新的业务生成并处理答案后才推进。问句、程序、宿主问题控件应表达同一问题，不能只展示一个泛化 Intent 就弹出无上下文选项。

**完成条件**：公开输入与问题回答入口的系统轨迹证明等待没有被非答案清空，独立请求可处理且原问题未丢失；工具 body 与副作用两处证明相关行动零执行。不能仅断言“缺 Intent 被拒”。

### P3：实现无粗暴失败的格式恢复（依赖 P0 验证通过的恢复路线）

采用 P0 已证实的官方入口，替换当前“首次合成 error → 默认终态 → idle followup”的用户交互。保持旧响应/参数/replay 不放行，唯一修复工具目录为空；接受声明后按最新问题状态继续澄清或业务。

普通 retry、静默重试叠加、给旧正文补前缀、在 stream hook 中私自递归请求模型、伪造用户继续均不采用。全局屏蔽 INTENT 错误码也不算修复。

配套用户文案明确“正在补全意图声明”；真正耗尽显示协议暂停，真实 provider 故障仍显示。若 P0 只能支持请求聚合路线，明确承认底层 turn 边界，不在日志造假。

**完成条件**：真实呈现端不先出现 Failed/This turn failed，业务不需用户重发；内部拒绝、usage、阶段与取消仍可追溯。P0 未通过时此包 BLOCKED，不能用截图裁剪或隐藏记录交付。

### P4：统一恢复、预算和资源保护（依赖 P2；涉及 P3 的路径依赖其结果）

正式记录区分问题待答、答案到达、仍需澄清、声明修复已用、声明已发布、业务待续、业务完成和取消。复用宿主日志/插件记录能力，先验证生命周期；不建立第二份私有事实源。

在“决定进入修复”时持久记账，排队失败、恢复或通用 retry 不新给预算。新用户输入可开启新的声明机会，但不能因此解决旧问题或重放旧调用。旧通知前缀兼容；新阶段通知不得都计为修复。

测四个断点：首次失配已判定但修复未排队、声明生成中、声明已提交但业务未调度、业务执行中。逐个验证取消/恢复/重载/压缩，不能用一次同进程恢复代表全部。

资源沿用当前 262144 字符、120000 ms、一次修复、声明正文 2000 字符作为待复核基线。区分正文上限、实际缓存占用、无 chunk 等待、provider 生成上限与总调用预算；若当前上限只在 finish 后判定，需补实际保护及释放证据。新数值有理由与测试后才改，截断不算声明无效。

**完成条件**：不重置预算、不丢问题、不重放；取消后待排队修复与业务零执行；usage 分段对账且 unknown 保留。无法可信恢复时明确暂停，不猜测批准。

### P5：系统、实际呈现与交付验收（依赖受测的 P1～P4）

沿用完整 preset、隔离打包安装、真实 launcher/registry/loader、AgentLoop/Session 与官方进程 PTC。保留 read/edit、默认编辑策略与其他运行约束。固定适配器只提供可控输出/竞争时序。

对旧测试逐项判断：保留仍有效契约；首次失败必须可见、任意输入结束等待等旧期望须按已修订规格更新。先观察新断言在旧实现失败，再实现转绿，不能只把旧 PASS 改写成新 PASS。

实际 CLI/Web 至少穿透支付澄清、首次失配修复成功、耗尽、取消和真实故障。仅 controller 原样转发帧不能代替真实 UI 没有 Failed 的证据。不能启动日常目标时，用隔离宿主；环境不足登记 GAP/BLOCKED。

完整验证按 README：`pnpm check`、`pnpm test:unit`、`pnpm test:integration`、`pnpm test:ptc`、`pnpm test:compat`、`pnpm check:preset`、`pnpm test:profile`、`pnpm test:host-gate --pack <新证据目录>`、`pnpm test:surface-gate --pack <另一新目录>`、`pnpm test:delivery`。构建只在验证副本；交付命令会写报告，避免覆盖用户当前同日证据。

**完成条件**：最终 Diff 的门禁、实际路径/补丁/资源摘要与逐条验收可追溯；未执行项明列，不能因工具目录或版本号相同就推定安装正确。
