## Problem Statement

用户需要在 agent 开始工作前看见它如何理解目标，以便及早发现误读，并让后续行动围绕明确目标。现有意图门依赖工具名、六桶首行及内层工具拒绝：纯解释可能不触发，含只读 shell 的程序却可能在执行途中才被拒绝。格式合规也不能说明 agent 理解正确。

用户希望普通明确请求能够直接推进；只有会改变目标、交付或重要行动的关键意图歧义，或无法自行查清的必需信息缺失，才停下来询问。用户不希望每个请求都先回复“继续”，也不希望因无关紧要的措辞或实现细节反复被打断。

缺少请求级状态还会使继续执行、用户纠正、自动修复与恢复混淆：旧声明可能遮蔽新要求，重载可能重置预算，澄清问题发出后也可能继续执行。需要一份明确区分意图声明、声明修复和澄清等待的行为契约。

## Solution

将意图门从按内层工具名拒绝，演进为请求级理解声明与执行前校验。每次需要声明的真实用户输入，由主 agent 在原有生成中检查目标、交付物、对象、范围和完成标准，用 `Intent:` 开头的自然语言说明目标与下一步，不再强制六桶分类。

首版严格要求需声明的正式回复正文先校验、后展示，工具实际执行也等待检查通过；接受部分首响应需要等整段生成完成，不承诺立即流式显示。机械检查只判断首行标记和非空正文，兼容大小写、空格差异；语义质量由主 agent 自检与独立效果评估负责，不增加第二个模型。

关键意图歧义列出有依据的合理解释和工作差异，必需信息缺失则直接询问缺失项。发问前可做必要且已获授权的只读核实，确定需要用户取舍就直接问；发问后暂停当前请求，其他独立请求不受影响。明确请求通过检查后直接继续，不等待逐次批准。

首次声明不合格时旧响应和旧调用不放行，最多自动修复一次；仍不合格则说明原因并停止。不同主会话隔离状态与预算；恢复保留澄清等待、已用预算及最新约束。无法可信恢复、资源超限或接口不能满足约定时，明确报告并停止或重新对齐，不静默降低要求。

## User Stories

1. 作为用户，我希望 agent 开始工作前具体说明我的目标，以便判断它是否理解正确。
2. 作为用户，我希望声明说明下一步做法，以便知道 agent 将如何推进。
3. 作为提出解释问题的用户，我希望纯文本答案也覆盖意图声明，以便误读不会因没有工具调用而被忽略。
4. 作为用户，我希望每次真实输入后的首次正式回复表达理解，以便新的要求得到处理。
5. 作为用户，我希望同一请求的工具续步、进度和收尾不重复完整声明，以便减少阅读负担。
6. 作为用户，我希望声明以固定标记开头并用自然语言说明内容，以便既能识别又容易阅读。
7. 作为用户，我希望无需阅读强制的英文六桶分类，以便把注意力放在实际理解上。
8. 作为用户，我希望大小写、空格差异不会单独导致拒绝，以便避免无意义的往返。
9. 作为审阅者，我希望格式合规与理解正确分开记录，以便不会把机械通过误当语义保证。
10. 作为用户，我希望 agent 自行处理等价实现和轻微细节，以便不被不必要的确认打断。
11. 作为用户，我希望会改变目标、交付或重要行动的多解得到澄清，以便选择真正需要的工作。
12. 作为用户，我希望各候选解释说明具体工作差异，以便能够作出选择。
13. 作为用户，我希望可以补充不在候选项中的意图，以便不被 agent 列出的选项限制。
14. 作为用户，我希望缺少无法自行查清的必需目标或参数时被直接询问，以便 agent 不编造信息。
15. 作为用户，我希望 agent 自己查清可获得的技术事实，以便不把查文件的工作推给我。
16. 作为用户，我希望澄清问题发出后当前请求暂停，以便回答前不会继续发生相关行动。
17. 作为用户，我希望暂停一个请求不影响其他独立请求，以便仍能开展明确的工作。
18. 作为用户，我希望推荐选项和沉默都不被当作我的选择，以便保留决定权。
19. 作为用户，我希望澄清中的“继续”不会替我选择 A 或 B，以便避免误执行。
20. 作为用户，我希望纯社交回应和目标清楚的正常继续可免重复声明，以便交互保持简洁。
21. 作为用户，我希望含新目标、约束或纠正的输入更新理解，以便新要求不会被旧声明遮蔽。
22. 作为用户，我希望中途纠正后旧的未执行调用先暂停并重新判断，以便行动遵循最新要求。
23. 作为用户，我希望已执行事实得到如实说明且不被自动回滚，以便不会丢失已有结果或他人改动。
24. 作为用户，我希望声明缺失时整段旧程序从未启动，以便不会在内层被拒前已发生部分副作用。
25. 作为用户，我希望 agent 有一次自动修复声明的机会，以便无需为普通遗漏手动介入。
26. 作为用户，我希望修复预算耗尽后明确停止，以便避免无限重试或无声明继续。
27. 作为用户，我希望失败后说“继续”能够重新尝试目标并重新声明，以便恢复任务而不重放旧调用。
28. 作为用户，我希望网络故障、超时和截断保持真实原因，以便不会被错误地归为声明问题。
29. 作为用户，我希望必要的系统错误提示无需强行包装意图声明，以便及时知道故障。
30. 作为用户，我希望取消后不执行缓存调用，以便停止行为具有实际效果。
31. 作为用户，我希望需声明的正式回复在通过检查前不展示，以便不会先读到未接受的正文。
32. 作为用户，我希望界面独立展示的思考和加载状态不被当作正式首句，以便无需为本机制改造全部界面顺序。
33. 作为用户，我希望额外等待能够被测量和评估，以便权衡严格检查的交互成本。
34. 作为多会话用户，我希望各主会话独立维护状态和预算，以便不会互相误伤。
35. 作为用户，我希望其他 preset、子代理和辅助模型调用不被本机制扩展，以便控制首版影响范围。
36. 作为用户，我希望恢复、压缩或重载后保留等待和预算，以便不会绕过规则或重复执行。
37. 作为用户，我希望无法可靠恢复状态时暂停并说明，以便不会在未知状态下继续。
38. 作为审阅者，我希望被拒生成的已知成本仍计入、未知成本明确标记，以便得到真实成本判断。
39. 作为维护者，我希望合格响应及其元数据保持保真，以便回放、日志和工具结果仍然可信。
40. 作为维护者，我希望缓存、时间及生成上限在工程设计中明确，以便资源使用有界且超限不绕过检查。
41. 作为用户，我希望意图声明不会扩大授权，以便没有打断不等于批准新增工作。
42. 作为维护者，我希望工程验收与效果评估分开，以便不会以声明出现率替代实际收益。
43. 作为维护者，我希望接口无法满足已确认行为时明确报告缺口，以便重新对齐而不是静默替代方案。
44. 作为维护者，我希望本规格保留既有 read/edit 和部署约束，以便意图门演进不顺带改变无关契约。

## Implementation Decisions

### 目标模块与架构约束

本次演进的对象是 `ptc-hashline` 的意图声明、persona 指引、执行前校验及请求状态协作，不重做 read/edit 引擎。依赖身份、有效工作目录、共享 hashline 实例、canonical value、工具名称和输出契约继续沿用既有约束。

通过官方插件扩展点组合实现是候选方向，不复制、fork 或修改 DSH 本体。输出流包装、声明修复、工具派发约束和会话状态需要作为完整组合设计；单独包装模型输出不能被宣称已满足中途纠正、澄清等待或恢复要求。

现有工具名门与六桶格式是待替代的运行基线；新旧校验不能因未迁移的双重约束使自然语言声明再次被旧六桶规则拒绝。演进需一并审阅 persona、意图门、资源摘要和关联契约，不顺带改变其他运行基线。

### 行为契约

| ID | 已确认要求 |
|---|---|
| IG-B-01 | 每次真实用户输入后的首次正式回复表达理解，包含纯解释；同请求工具续步、进度和收尾不重复。新目标、约束或纠正仍须更新理解。 |
| IG-B-02 | 规范首句保留 `Intent:`，后接自然语言目标与下一步，不强制六桶。硬校验仅查首行标记和非空正文，兼容大小写、空格差异。 |
| IG-B-03 | 主 agent 在原有生成中检查目标、交付物、对象、范围及完成标准，只考虑有依据且会导致不同工作的解读，不增加第二个模型。**歧义是正常交互，不是输入错误**：合理的多解输入必须得到「列出有依据的解读及其工作差异 + 询问真实意图」，不得显示为 error、不得当成校验失败或停止原因；必需信息缺失时直接问缺失项；普通明确请求、等价实现与可自行查清的事实直接推进，不增加往返。 |
| IG-B-04 | 需声明的正式回复正文在展示和提交前校验，工具实际执行也等待通过；独立思考内容和加载状态不纳入首句。首版严格展示优先，可延后显示。 |
| IG-B-05 | 首次校验不合格时旧响应与旧调用一律不放行，且**请求层不把这次失配当成用户请求的结论**：用户最多看到一次「正在补全意图声明」的恢复状态，看不到「本次请求失败 / This turn failed」式的终态宣告；恢复过程中不发布旧正文、不执行旧调用、不放行旧工具参数；唯一一次修复是**声明专用生成**：同一受管主 agent、该次请求不提供任何行动工具、只接受非空声明正文及允许的独立 reasoning（reasoning 与工具参数不算正文）。即使适配器违规输出工具调用，也要在发布与派发之前拒绝。插件不伪造理解、不重放旧调用、不拼接旧正文。 |
| IG-B-06 | 每次需要声明的用户输入最多自动修复一次，且该次修复必须在决定进入时记账，不因后续故障或重试策略放大。修复仍不合格（无正文、缺标记、空正文、违规工具或超出专用输出约定）则停止自动生成并说明「意图声明未能生成、工作尚未执行」，属可恢复的**协议暂停**，不伪报业务完成、不无声明继续。正常任务续步不计声明修复；声明合格后的业务续步不是第二次修复，不新给修复预算。取消、拒绝、超时与真实故障不打开修复；取消后排队中的修复与业务续步必须零执行。 |
| IG-B-07 | 修复提示明确记录为插件来源，先给出声明专用阶段的输出约定、再声明原请求与授权不变，不伪装用户授权、不暗改冻结请求；重生成上下文可从正式记录重建。续步提示同样是插件来源，且不重置预算。**提问也走插件可判读的正式路径**：问题经 `tools.ask_user_question` 提出，问句、程序内容与宿主问题控件表达同一个问题；插件消息永远不是用户回答。 |
| IG-B-17 | 声明合格后先正式记录并发布声明，再由**同一请求**在后续步骤生成业务响应；业务生成可正常使用工具，但工具实际执行必须发生在声明发布之后。续步不要求重复声明、不再消耗修复预算，旧生成的工具参数与 replay 不移植到续步。真实用户追加约束优先于旧声明的续步。续步开始时若仍有未解的业务歧义或待答问题，则进入澄清而不是直接执行：格式恢复完成不等于理解已被确认，也不等于已获准执行。 |
| IG-B-18 | 成本与诊断分开且可对账：初次失败、声明修复、业务续步三段成本分别记录，未知成本仍记 unknown。声明专用阶段的正文上限与 provider 的生成上限分别声明（截断按 provider 原始终态处理，不改写成声明不合格）。诊断只记录请求/阶段/失配类别/原 finish.kind/各块计数/正文空标志/预算/usage/耗时/有效上限，不保存被拒正文、reasoning 原文或工具参数，也不伪装成被接受的答案。问题阶段不计入修复次数，也不因提问、等待或恢复另给预算。 |
| IG-B-19 | 提问与业务动作分开：允许只承载 `tools.ask_user_question` 的 `run_code` 程序；该程序拿到答案后，同一程序内不得再执行依赖答案的业务工具（读取、写入、派发、委派等），相关动作必须由处理答案后的新生成发起；问题未解决前也不执行该请求的相关业务工具。 |
| IG-B-20 | 请求层呈现分档且互不冒充：需要澄清→显示合理解释、工作差异与具体问题并等待；正在内部修复格式→显示恢复状态，不发布旧正文、不执行旧调用；修复成功→发布已接受的真实声明，并按仍存在的等待与最新约束继续；修复耗尽→「意图声明未能生成，工作尚未执行」的有界协议暂停；provider 故障、取消、截断、超限→各自真实原因，不伪装成缺声明、不自动获得新预算。 |
| IG-B-08 | 同任务新目标或约束到达时，旧未执行调用先暂停，按新要求重判并更新声明再继续；已执行动作不自动回滚。 |
| IG-B-09 | 声明、分类及用户未打断均不扩大授权；方法和初始假设可被新证据修正。等价实现和轻微细节由 agent 自行判断。 |
| IG-B-10 | 取消、网络错误、模型超时与截断沿用宿主处理，不一律视为缺声明，不额外消耗声明修复次数；必要系统错误提示免标记，取消后不执行缓存调用。 |
| IG-B-11 | 原 provider 完成、插件拒绝与真实故障分别记录；被拒生成的已知成本仍计入，未知成本记 unknown，不伪报零成本。 |
| IG-B-12 | 合格响应保留原正文、工具参数、usage 和 replay 元数据；被拒元数据不挂到新答案，不制造未执行工具的结果。 |
| IG-B-13 | 仅本 preset 的受管主 agent 生效，不扩展其他 preset、子代理及辅助调用；不同主会话独立维护状态和预算。 |
| IG-B-14 | 恢复、重载与压缩保留澄清等待、已用预算和最新约束，不重放旧调用；状态无法可信恢复时暂停并说明。**待答状态按问题身份保存**（外层 `tool/call` 的 callId 或 PTC 内层 subCallId），并记录它属于哪个请求，不以「本会话有没有问过问题」的单一布尔值代替；恢复后错配的结算、陈旧结果与另一会话的结算都不得解锁。 |
| IG-B-15 | 工程设计必须列明缓存、时间、生成上限和测时方式；触及本机制资源上限时暂停说明，不绕过校验放行。**上限必须在生成尚未结束时就能生效**：不能只在收到 finish 之后才判定，因此需要真实的时间保护与来源释放（已收到的字节丢弃、不发布），只把 provider 已报的 usage 转出去，成本仍可见。接口不足则报告缺口重新对齐，不擅自降级。 |
| IG-B-16 | 关键意图歧义或无法自行查清的必需信息缺失时澄清；发问前可必要且获授权地只读核实，需要用户取舍就直接问；发问后暂停当前请求，其他独立请求不受影响。**暂停只能由该问题自己的答案或宿主结算结束**：「继续」「收到」、空白、沉默、插件通知、其他工具的结算、指向别的问题或会话的陈旧结果都不算答案，也不能替代选择；显式选择与自由文本都是答案，选项标签恰好叫「继续」时必须按真实选择处理。用户明确取消原目标时该目标的等待随之结束（不保留永久锁），但取消不是选择，不能冒充答案。 |

### 例外与状态优先级

- “谢谢”“收到”等纯回应不需声明；目标清楚的正常“继续”承接已有理解，不重复整句。按语义处理，不只匹配关键词。
- 回答澄清选项须结合待答问题解释，不能误当纯社交确认；A/B 待答时单说“继续”不算选择，不默认接受推荐项，沉默也不算同意。
- 声明修复耗尽后的“继续”覆盖普通继续的免声明例外：重新声明与生成响应，获得一次新修复机会，不重放旧调用。
- 协议暂停（声明专用修复仍未产出合格声明）等于「声明未生成、工作未执行」：它不升级为业务失败，也不要求宿主新增 turn/end 类型；用户重新发起请求才是新的声明机会，自动续步、恢复、压缩和插件通知都不能冒充该机会或重置预算。
- 用户主动继续可触发上述新机会；恢复、压缩或重载本身不能清空已用预算。主会话之间也不能借用或重置预算。
- 原模型调用未正常完成时先保留其真实故障语义，不因没有完整声明就额外启动声明修复。修复预算不能被其他重试策略放大。
- 已发出澄清问题的当前请求暂停；其他独立请求和会话不应被永久锁住。关联与调度需要请求级设计，不能靠全局等待标记代替：等待记录必须带上问题身份（callId / subCallId）与所属请求，非答案输入只开启自己的声明义务，不清空旧问题，也不把它变成「已选择」。
- 澄清是正常交互：等待中的请求不显示失败、不显示错误码，也不因为「模型在提问」而被当作协议暂停。
- 中途纠正只暂停旧未执行调用，不改写已执行事实，不承诺整个程序事务回滚；意图门不是完整权限或安全隔离机制。

### 机械检查与语义质量

机械检查不推断理解正确。只有标记和非空正文的短句仍可能机械通过，却不满足具象化理解的内容要求；该差异必须在日志解释和效果评估中保留。

主 agent 对多解说明各候选会交付或改变什么，可给推荐理由并允许用户另行补充。缺少单项必需信息则直接问该项，不编造两种意图。技术事实先自行核实，目标与取舍交给用户；不为每个请求硬凑歧义。

### 留待工程评审的选择

精确匹配规则、多文本块与首行解析、缓存数值、超时和生成上限、官方接口组合、策略失败分类、请求身份与持久化结构、恢复可信性及用户提示措辞，均需由后续工程设计明确并可审查。本文不预先锁定代码结构、钩子组合或数据 schema；未定不能解释为无限制。

最终文本可能覆盖流中的临时文字，不能通用地以首个换行认定最终声明已稳定。可以选择满足严格要求的暂存方式；不能为低延迟先放行不确定正文而静默弱化本规格。接口不能满足时返回重新对齐流程，不将纯工具拒绝或仅改提示当成等价替代。

## Testing Decisions

### 用户已确认的主要 seam

采用一个主要系统级 seam：从用户对装有完整 preset 的真实宿主发出输入，到正式回复呈现、真实工具执行及会话恢复的外部行为。复用隔离打包安装与官方 launcher/registry/loader，保留完整目标 preset、真实 AgentLoop/Session 和官方进程 PTC；固定响应适配器提供可控模型输出，不移除既有 read/edit、persona 或其他运行策略来制造通过。

固定适配器可控制分块、失败、取消和竞争时序，真实用户来源输入通过公开 followup/steering 等入口进入。不直接改插件私有状态作为主要验收步骤，不以私有字段、单个 hook 或正则返回值代替外部行为。

正式正文的展示前保证需在实际 CLI/浏览器呈现端作最小穿透检查。输出呈现、会话记录、工具入口和副作用是同一系统 seam 的观察面；后台发布正确不能自动证明用户界面正确。

## Out of Scope

- 增加独立的语义审核模型，或保证自动识别所有误解与歧义。
- 要求每次普通明确请求都等待用户回复“继续”，或将推荐、沉默视为批准。
- 强制六桶分类，将声明作为权限、安全隔离或原子事务保证。
- 首版扩展到其他 preset、子代理或辅助模型调用，改造所有界面思考/状态展示顺序。
- 自动回滚已执行动作、恢复旧调用执行，或绕过工具观察路径改变状态。
- 重做 read/edit、改变工具名、canonical value、cwd、共享引擎、seen/tag、BOM/MV 等既有契约。
- 复制、fork 或修改宿主本体；为通过测试仅改运行中的依赖。
- 在规格阶段锁定缓存字节量、超时秒数、状态 schema、接口组合或完整实现计划。
- 本轮产品实现、构建/安装、宿主重启、发布、升级目标切换，以及真实模型效果试验或恢复已收尾的 S0/S1/S2。
